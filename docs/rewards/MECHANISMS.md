# Reward mechanisms and wizard diagnosis

2026-10-09. No live funding or claim transaction was submitted.

## Creator and recipient routes

ERC-20: exact aggregate allowance to RewardEngine, depositERC20, then Code allocation or immutable Merkle membership or public allocation. Amounts are base units. ETH: depositETH with exact value; no allowance. ERC-721: free balanceOf + tokenOfOwnerByIndex where supported, otherwise pasted IDs verified by ownerOf. Select one or up to 50 distinct held IDs; each is a separate per-winner asset in one pool. The deployed ABI has no batch deposit, so multi selection uses a resumable sequence of approve(engine, tokenId) and depositERC721 transactions. It never requests setApprovalForAll for ERC-721. An on-chain atomic batch deposit is not available yet. ERC-1155: one ID and quantity, standard collection-wide setApprovalForAll then depositERC1155; the UI explains scope and revocation. Metadata is optional tokenURI / uri, fetched client-side with a timeout, no paid indexer or server-side URL fetch. Unreadable metadata never invents an image.

Code/Auto-prompt game prizes require server-confirmed rankings then creator-confirmed setAllocation. Auto-prompt uses Code on-chain and requires a recipient transaction; contract AutoPush is not used by the wizard. Each reward card names the collection, exact NFT ID, recipient, deadline and wallet call. Only a confirmed receipt is labeled claimed. Multiple Code allocations use allocationInfo per slot, not the pool-wide isClaimed flag.

Merkle drops commit fixed wallet / assetIndex / amount leaves before funding. Distinct NFTs use distinct indices in deposit order; repeated fungible assets aggregate. Leaves match RewardEngine's single keccak packed address + uint256 index + uint256 amount, with sorted sibling pairs. One claim per wallet, up to 50 distinct recipients. A waitlist drop uses the owner-only waitlist-rewards API; deduplicated nonzero wallets include both winners and non-winners. Prepare/publish validates source ownership and recipient membership. The creator freezes the snapshot at funding; later entries cannot change the root. Claims appear in My rewards without game entitlements or a finished match. Public Open drops likewise appear for signed-in wallets; creator confirms the public allocations after publication. One claim per distinct wallet on the hardened contract. A wallet cap is not a Sybil-resistance guarantee.

V4 Boss Raid / Token Catch game payouts remain single-asset ERC-20 shared pools. NFTs and ETH cannot be divided by their contribution math; the wizard explains this restriction and permits independent drops. Private-key delivery and a paid wallet NFT indexer are not available. Never enter a private key in a reward configuration. All assets remain claimable through the deadline; only remaining per-pool inventory is reclaimable afterwards on the hardened source.

## Reproduced broken paths

Live Chromium at https://orbixcore.fun/center/create/combat-duel verified API-backed wizard load with zero JS errors. The old preview reward selectors only changed explanatory panels; they did not activate the actual funding settings. These selectors now open the real per-type form. The old ERC-721 configuration accepted exactly one slot; the new selector builds distinct NFT slots. The old Merkle claims required a game entitlement and one shared asset, preventing waitlist/non-winner drops and multiple NFTs. Separate distribution mode now fixes both. Preparing an invalid/disabled funded publication used to save and lock an attempt before the API returned; now the API prepares first. Stale attempts with no funding journal/pending hash can be reopened for editing. Attempts with submitted transactions retain their original configuration and resume.

Live eth_call reads on Robinhood 46630 verified the documented engine address, authority and poolCount=0, and safetyVersion() reverted. This proves neither updated bytecode nor funded execution. Phase O introduces a fail-closed safety capability check so source changes cannot be mistaken for a deployed fix. A new hardened deployment and synchronized client/server configuration are necessary before new funding; this session does not deploy contracts or Railway.

Tests: real local API auth in tools/tests/rewards-wizard-browser.cjs with mocked free NFT reads; backend Merkle/drop/source authorization tests; mocked wallet multi-NFT approvals/deposits/receipts. No wallet spend. Non-enumerable collections use manually verified IDs; RPC/indexer completeness and physical wallet/device behavior are not asserted.
